# API Design Skill — RESTful API Contract

## Purpose

Use this skill whenever designing, implementing, refactoring, reviewing, documenting, or testing HTTP APIs in this project. **Treat MUST, MUST NOT, and SHOULD as normative requirements.**

The goals are:

1. Model domain **resources**, not RPC commands.
2. Use HTTP methods and status codes according to their actual semantics.
3. Return a predictable JSON envelope with **exactly three top-level fields** for responses that have bodies: `data`, `code`, and `timestamp`.
4. Make errors actionable for a non-technical receptionist without exposing implementation details.
5. Keep backend business-rule validation authoritative across **all rooms, tutors, and students**.

## 1. Required response format

All application JSON response bodies MUST follow this structure:

```json
{
  "data": {},
  "code": {
    "http_status": 200,
    "key": "SUCCESS",
    "message": "Request completed successfully"
  },
  "timestamp": {
    "iso": "2026-03-07T10:30:00Z"
  }
}
```

### Field contracts

| Field | Type | Rules |
|---|---|---|
| `data` | JSON object | MUST always be an object. On success, contains the resource or a collection object; on error, use `{}` or structured error details. Do not use a bare array at the top level. |
| `code` | JSON object | MUST contain `http_status` (integer), `key` (stable uppercase `SCREAMING_SNAKE_CASE` identifier), and `message` (human-readable string). |
| `timestamp` | JSON object | MUST contain `iso`: a valid RFC 3339 / ISO 8601 instant, preferably UTC with `Z`, generated by the server at response time. |

**Rules:**

- The HTTP status line is the **source of truth**. `code.http_status` MUST equal the actual HTTP response status; it does not replace HTTP status codes.
- The envelope applies to **responses with JSON bodies**. A `204 No Content` response MUST have no body. Likewise, responses with bodyless HTTP semantics (e.g., `304 Not Modified`, `HEAD`) MUST NOT be forced into the envelope.
- Always set `Content-Type: application/json` for JSON responses.
- Do not wrap client requests in this envelope unless an endpoint explicitly documents doing so; normal request bodies are resource representations or change sets.
- `code.key` is stable for clients; `code.message` may be revised for readability. Never use stack traces or SQL errors as public messages.
- For list responses, use an object such as `data: { "items": [...], "pagination": {...} }`.

## 2. REST resource and method conventions

- Paths MUST use plural nouns and stable resource identifiers: `/api/v1/bookings`, `/api/v1/bookings/{lesson_id}`.
- MUST NOT use action-like routes such as `/createBooking`, `/reschedule`, or `/cancelBooking` for ordinary resource mutations.
- `GET` MUST be read-only, safe, and idempotent.
- `POST` to a collection creates a resource. Return `201 Created` and a `Location` header.
- `PATCH` partially updates a resource (including date/time changes or changing its `status` to `cancelled`). Return `200 OK` with the updated representation, or `204 No Content` with no body.
- `PUT` replaces the full resource representation when supported; MUST be idempotent.
- `DELETE` removes a resource only when deletion is the intended domain operation. **Booking cancellation is a state transition, not deletion:** use `PATCH /api/v1/bookings/{id}` with `{"status":"cancelled", ...}`.
- Use query parameters for collection filtering, not action routes: `GET /api/v1/bookings?from=2026-03-03&to=2026-03-10&room=R1`.
- Never change server state via `GET`.
- API resource identity MUST remain stable through same-room rescheduling; log the change rather than creating a new booking.
- Cross-room moves in this MVP are an explicit **cancel-old + create-new** client workflow (two independent operations), not an atomic transfer. Do not pretend it is transactional across both calls.

**Important:** No tutor-based calendar view is required. Tutor availability still MUST be validated across every room.

## 3. HTTP status semantics

| HTTP status | When to use | Example |
|---|---|---|
| `200 OK` | Successful read or update returning a representation | `GET` bookings, `PATCH` booking |
| `201 Created` | Resource successfully created | `POST /bookings` |
| `204 No Content` | Successful operation with **no** response body | `PATCH` with no representation returned |
| `400 Bad Request` | Malformed request syntax or invalid JSON | Malformed JSON document |
| `401 Unauthorized` | Authentication is required or invalid | Missing/invalid credential when auth exists |
| `403 Forbidden` | Authenticated caller lacks permission | Non-staff user tries to edit |
| `404 Not Found` | Requested resource does not exist | Unknown `lesson_id` |
| `405 Method Not Allowed` | Resource exists but requested method is unsupported | `PUT` to a read-only collection; include `Allow` header |
| `409 Conflict` | Requested state conflicts with existing state | Tutor/student/room overlap, tutor daily capacity, invalid lifecycle transition |
| `412 Precondition Failed` | Conditional request (`If-Match`) does not match current version | Booking changed since it was displayed |
| `415 Unsupported Media Type` | Unsupported request payload content type | Request content type not JSON |
| `422 Unprocessable Content` | Syntactically valid request fails intrinsic/domain input rules independent of competing bookings | `duration_min: 45`, Monday booking, missing required field |
| `428 Precondition Required` | Server requires a conditional request | Missing mandatory `If-Match` on `PATCH` |
| `429 Too Many Requests` | Rate limit exceeded (if implemented) | Throttled requests; include `Retry-After` when applicable |
| `500 Internal Server Error` | Unexpected server failure | Unhandled internal error (never leak details) |
| `503 Service Unavailable` | Temporary service unavailability | Database temporarily unavailable |

Do not respond with HTTP `200` when the operation failed. Do not use `500` for predictable validation or scheduling conflicts. Do not use `404` for invalid JSON.

### Versioning and concurrent edits

- Prefer a standard ETag for each booking representation: `ETag: "booking-L001-v3"`.
- For updates, clients SHOULD send `If-Match: "booking-L001-v3"`.
- If a provided `If-Match` fails, return `412 Precondition Failed`, not `409`.
- If a precondition is mandatory but missing, return `428 Precondition Required`.
- Concurrent booking conflicts that survive version checks return `409 Conflict`.
- Perform validation and writes atomically in a database write transaction. Never implement a check-then-write race.

## 4. Booking domain rules

All mutations MUST be validated **on the server**, whether initiated via the form or the room-based calendar drag-and-drop UI.

1. Duration MUST be **60 or 90 minutes**.
2. The centre operates **Tuesday through Sunday**; Monday is closed. Preserve historical Monday records when importing the seed.
3. One student cannot occupy overlapping lessons.
4. One tutor cannot occupy overlapping lessons **in any room**.
5. One room cannot host overlapping active lessons.
6. A tutor may have at most **six counted bookings per day** under the documented rule; paired-lesson counting remains an owner question.
7. `cancelled` bookings release the occupied slot; `no_show` bookings retain it.
8. Same-room rescheduling changes the existing booking's date/start time and preserves its room and duration when dragged. Form editing may change documented editable attributes, subject to validation.
9. All accepted modifications and cancellations MUST be persisted with an immutable booking-change record in the same transaction.
10. Changes after the **16:00 previous-day schedule cut-off** remain permitted but must be traceable; successful persistence MUST NOT be described as successful notification delivery.
11. Do not invent numeric opening/closing hours or approve paired lessons without owner clarification.
12. Existing CSV seed records MUST be imported unchanged; do not “fix” historical rule violations automatically.

Overlap predicate (using half-open intervals):

```text
existing.start < candidate.end AND candidate.start < existing.end
```

When editing a booking, exclude that booking ID from its own overlap check. Validate tutor and student conflicts against the complete dataset, not merely the currently selected room.

## 5. Request/response examples

### Create booking

```http
POST /api/v1/bookings HTTP/1.1
Content-Type: application/json

{
  "student": "Le Minh Chau",
  "tutor_id": "T2",
  "room": "R2",
  "date": "2026-03-07",
  "start_time": "13:00",
  "duration_min": 90
}
```

Response: `201 Created`, `Location: /api/v1/bookings/{new_lesson_id}`, JSON envelope.

### Same-room reschedule

```http
PATCH /api/v1/bookings/L001 HTTP/1.1
Content-Type: application/json
If-Match: "booking-L001-v1"

{
  "date": "2026-03-03",
  "start_time": "13:00"
}
```

Response: `200 OK` plus the updated booking envelope and the new `ETag`; `409` for an availability conflict, `412` for a stale `If-Match`.

### Cancellation (including administrative room change)

```http
PATCH /api/v1/bookings/L001 HTTP/1.1
Content-Type: application/json
If-Match: "booking-L001-v1"

{
  "status": "cancelled",
  "reason": "administrative_room_change"
}
```

Response: `200 OK` plus the updated booking envelope. A subsequent `POST /api/v1/bookings` creates the new room booking after normal validation. **This two-step process is not atomic and is not automatically a billable family cancellation.**

## 6. Implementation and review checklist

Before considering any API ready, verify:

- [ ] The method and URI describe a resource operation with correct REST semantics.
- [ ] The actual HTTP status matches the result; `code.http_status` matches it exactly.
- [ ] All JSON response bodies include `data`, `code`, and `timestamp` objects; bodyless statuses have no body.
- [ ] Errors use stable `code.key` identifiers and receptionist-friendly messages.
- [ ] Input validation rejects missing/invalid fields with an appropriate 4xx status.
- [ ] Booking conflict validation covers all rooms, tutors, and students.
- [ ] Create, update, cancellation, and audit persistence are transactionally correct.
- [ ] Concurrent or stale modifications cannot silently overwrite another valid update.
- [ ] The CSV seed remains intact, including historical anomalies.
- [ ] Endpoints have reproducible success and error tests and are documented in the README or API reference.

## 7. Non-goals

Do not add RPC-style endpoints, a separate tutor calendar API, message brokers, automatic WhatsApp notification delivery, a billing engine, or cross-room drag-and-drop under this skill. New requirements must be explicitly approved rather than inferred from the UI.
